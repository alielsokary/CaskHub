⏺ Confirmed the gotcha: CategoryService.swift:37 fetches
  releases/latest/download/categories.json. GitHub's releases/latest points at
  the most recently created full release — so the first cask-* icon release we
  publish would hijack it and break category updates. The fix is built into
  GitHub: releases marked pre-release are excluded from latest. All icon
  releases get published as pre-releases. One flag, no CaskHub change.

  Here's the design:

  1. Release scheme (in CaskKit)

  - Per-cask release: tag cask-<token>, single asset AppIcon.png, marked
  pre-release so data-* releases keep owning releases/latest.
  - URL shape identical to App-Fair:
  github.com/alielsokary/CaskKit/releases/download/cask-<token>/AppIcon.png.
  - Icon published once per cask. No re-extraction on version bumps in v1 —
  icons rarely change. (ponytail: re-extract-on-update deferred until someone
  notices a stale icon.)

  2. Extraction protocol (documented as docs/ICON_EXTRACTION.md — this is your 
  "protocol")

  Per cask, from cask.json metadata:

  1. Skip non-app casks (artifacts has no app/suite/installer-with-app) → record
  no_icon with reason.
  2. Download the artifact (vendor URL from the cask definition).
  3. Expand without executing anything: hdiutil attach -nobrowse -readonly for
  DMG, ditto -xk/unzip for zip, tar for tarballs, pkgutil --expand-full for pkg
  (extracts payload, runs no scripts).
  4. Locate the .app, read CFBundleIconFile from Info.plist, convert the .icns →
  256px PNG via sips.
  5. No .icns but CFBundleIconName present (asset-catalog-only app) → record
  car_only and skip in v1. The AssetCatalogTinkerer/CoreUI trick becomes a v2
  fallback only if the car_only count in the report justifies it — my bet is
  it's small, since Xcode compiles an .icns into macOS app bundles even from
  asset catalogs.
  6. Detach/clean up, publish release, append to report.

  Everything is stock macOS tooling orchestrated by Python — same language and
  style as the rest of scripts/.

  3. Pipeline & state

  - New scripts/extract_icons.py + workflow extract-icons.yml on a macOS runner
  (free for public repos), daily cron, independent of the classification
  workflow.
  - Source of truth for "done" = the releases themselves (one API page-through).
  A committed data/icon_report.json records no_icon / car_only / failed tokens
  with reasons, so known-hopeless casks aren't re-downloaded every day.
  - Batch cap per run (e.g., 50 casks) to bound runner time and be polite to
  vendor servers.

  4. Rollout — your plan, verbatim

  1. Local subset (~20 hand-picked casks covering dmg/zip/pkg/tar + a font + a
  binary) → verify PNGs by eye.
  2. CI subset: same list through extract-icons.yml with manual trigger,
  publishing to real releases.
  3. Backfill: run locally from your Mac in batches (the full artifact download
  is likely 100s of GB — friendlier from home than CI), publishing via gh 
  release create --prerelease.
  4. Flip on the daily cron for new casks only.

  5. CaskHub side (one small change, later)

  CaskIconURL chain becomes: CaskKit release → App-Fair release (also original
  icons) → placeholder. The avatar/favicon fallbacks get deleted once coverage
  is high — that's the "no generated icons" end state, and it's a separate small
  PR in CaskHub.

  CaskKit's docs/ and we move to planning.
